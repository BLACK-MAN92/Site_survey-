Executive SummaryField engineers currently perform tower-site clean-up surveys and report them manually: a shared Excel workbook (DAILY REPORTING TEMPLATE.xlsx) is filled row-by-row per site, and a separate PowerPoint deck (IHS_EDO_0067C.pptx) is assembled per site containing "Before pictures" and "After pictures". Photos travel by WhatsApp and email, the spreadsheet is version-conflicted across engineers, and there is no verifiable proof that an engineer was physically on site.This product replaces that workflow with a Flutter mobile application for field engineers and a web back-office dashboard for supervisors. Sites are pre-assigned to named engineers via an Excel import that carries the site ID, its coordinates, and the assigned engineer. Each engineer sees only their own sites. The same engineer performs both the pre-survey (site condition before works, scope of required work) and, after works, the post-survey (works completed, after photos) for a given site. Every submission is GPS-stamped, timestamped, attributable to a named engineer, and works offline-first because tower sites frequently sit outside data coverage.Submissions pass through a two-tier review: the back-office engineer first accepts or rejects internally, then records the outcome of the client's (IHS) own review. Both rejection types are raised by the back-office user and both push the site back onto the engineer's queue with the reason attached.The platform reproduces both existing deliverables automatically: the daily reporting XLSX export (identical 37-column schema) and the per-site before/after PPTX deck, generated from a combined pre/post view where the back-office can adjust, label and download the site's photos.1.1 Problem statement#Problem todayConsequenceP1Data entered into a shared Excel file by multiple engineersVersion conflicts, overwritten rows, lost daily reportsP2Photos sent via messaging apps, manually sorted into decksHours of manual deck assembly per site; Core User Flows3.1 Flow A — Pre-survey (Field Engineer)Engineer logs in (credentials persisted; biometric unlock thereafter).Home screen shows My Assigned Sites — and only sites assigned to this engineer, enforced server-side — split into Pre-survey due, Post-survey due, Rejected — rework, Draft, Pending sync. There is no site search or browse across the wider portfolio.Engineer taps a site → app requests/verifies location permission (mandatory) → captures GPS fix.App compares the captured coordinate against the site's registered coordinate:Within geofence radius → green "On site" badge.Outside radius → warning; engineer must select a reason from a list (e.g. Site coordinate incorrect, Access blocked, surveyed from gate) before proceeding. Submission is flagged for back-office review.Engineer fills the Pre-Survey form (Section 4.2): site metadata auto-filled from master data, then each of the 13 work items marked Required: Yes/No, plus planned clean-up date and comments.Engineer captures Before photos — camera-only capture (no gallery import) to guarantee authenticity. Minimum photo count enforced per configured rule. Each photo is EXIF-stamped and watermarked with site ID, timestamp, and coordinates.Engineer submits. If online → uploads immediately. If offline → queued locally with a "Pending sync" badge; the engineer may continue to the next site.3.2 Flow B — Post-survey (Field Engineer)The post-survey is performed by the same engineer who filed the pre-survey. The site appears in that engineer's Post-survey due list and in no one else's; the server rejects a post-survey whose author differs from the pre-survey author, unless the site has been formally reassigned (Flow D, §3.4).Engineer returns to the same site after works. Home screen lists it under Post-survey due with the pre-survey summary attached.Engineer opens Post-Survey form. The form is pre-populated with the pre-survey's scope: only work items marked Required = Yes at pre-survey appear as actionable.For each required item, engineer sets status WIP / Closed (and Qty replaced for Security Light). Items not required at pre-survey are shown collapsed and read-only; an "Add unplanned work item" action allows adding scope discovered later, which is flagged as a scope variation.Engineer records Actual Clean-up Date and overall Status (Closed / WIP / Pending).Engineer captures After photos. The app displays each corresponding Before photo as a framing reference so the after shot matches the angle.Submit → same sync behaviour as pre-survey.3.3 Flow C — Back-office reviewSupervisor opens dashboard; Submission queue sorted newest-first, filterable by date, zone, state, SMC, engineer, phase, status, rejection type, geofence-flag.Supervisor opens the Site Consolidated View — pre-survey and post-survey for that site on a single screen (§4.6.2): site header, scope table showing Required against Delivered item by item, and both photo sets paired for comparison. This is the working surface for review, photo adjustment, and deck generation; the supervisor does not need to open two records.Supervisor reviews the photos, corrects orientation/crop/brightness where needed (§4.6.3), and labels each photo.Supervisor issues a verdict (§4.6.5):Approve → the site is internally accepted and becomes eligible for submission to IHS.Back-office rejection → internal quality failure (photos unusable, scope mismatch, geofence flag). Never leaves the organisation.IHS rejection → the supervisor records that the client rejected the submitted site, with the client's reason and reference.Both rejection types return the site to the same engineer's queue as Rework, with a push notification carrying the reason.Supervisor generates the labelled per-site PPTX deck, downloads the site's photos as a ZIP, and exports the Daily Report XLSX for a chosen date/zone.3.4 Flow D — Site assignment & reassignmentAdmin/PM imports the pre-assignment spreadsheet (§4.1.1) containing site ID, coordinates, and the assigned survey engineer's name. The importer matches engineer names to user accounts and reports unmatched rows before committing.Each imported site is bound to exactly one engineer. That binding drives the mobile "My sites" list and is enforced on every API call.When an engineer is unavailable (leave, resignation, workload rebalance), a PM/Admin reassigns the site from the dashboard, supplying a reason. The action is written to the audit log.Reassignment consequences:If no pre-survey exists, the site simply moves to the new engineer's queue.If a pre-survey exists but no post-survey, the new engineer inherits the site and the post-survey scope; the survey records both the original and current engineer so the daily report and deck attribute the work correctly.Unsynced drafts on the previous engineer's device are invalidated on next sync, with an on-screen explanation.Bulk reassignment (all sites from engineer A to engineer B, optionally filtered by zone) is supported for the leave/resignation case.3.5 Flow E — Sync (background)Connectivity listener detects a usable connection.Queue drains in FIFO order: survey payload first, then photos (chunked, resumable, with exponential backoff).Conflict rule: server rejects a duplicate (siteId, surveyType, engineerId) submission; the client surfaces it as a conflict for the engineer to discard or convert to a revision.On success the local record is marked synced; photos are removed from the local cache after a configurable retention window (default 7 days).4. Both are stored. Required accuracy ≤ 50 m; below that the app prompts "Waiting for better GPS signal" with a manual override that flags the submission.FR-4.3.3 Captured fields: latitude, longitude, accuracy (m), altitude, provider, device timestamp, and server-received timestamp.FR-4.3.4 Mock-location detection: on Android, Position.isMocked is checked; a mocked fix flags the submission for mandatory back-office review.FR-4.3.5 Distance from the site's registered coordinate is computed and stored. Beyond the geofence radius, a reason code is mandatory.FR-4.3.6 Each photo carries its own coordinate at capture time, independent of the form-level fix.4.4 Photo captureFR-4.4.1 In-app camera only for survey photos; gallery import disabled to prevent submission of photos not taken on site.FR-4.4.2 Photos are categorised: before (pre-survey) or after (post-survey), and optionally tagged to a specific work item.FR-4.4.3 Minimum 6 and maximum 20 photos per survey (configurable per project phase).FR-4.4.4 Client-side compression to ≤ 1920 px on the long edge, JPEG quality 80, target ≤ 500 KB per image, before queueing for upload — critical on metered rural connections.FR-4.4.5 A visible watermark is burned in: Site ID, date-time, lat/long. EXIF is preserved in the stored original.FR-4.4.6 Post-survey capture screen shows the matching Before photo as a ghost overlay/reference thumbnail to encourage matching angles.FR-4.4.7 Uploads are resumable and retried; a partially uploaded survey is never visible to the back-office as complete.4.5 Offline-first behaviourFR-4.5.1 All assigned sites and their master data are cached locally on login and refreshed on each successful sync.FR-4.5.2 Surveys and photos are written to a local store (Drift/SQLite for records, filesystem for images) and enqueued as outbox items.FR-4.5.3 Sync runs (a) on connectivity regained, (b) on app foreground, (c) on a periodic background task, and (d) on manual pull-to-refresh.FR-4.5.4 The UI always shows per-record sync state: Draft, Queued, Uploading (n/m photos), Synced, Failed, Conflict.FR-4.5.5 Failed items retry with exponential backoff and never block later items indefinitely; after 5 failures the item is surfaced for manual retry.FR-4.5.6 Uninstall/reinstall warning: unsynced data is lost. The app warns when unsynced items are older than 48 hours.FR-4.5.7 Records are keyed by a client-generated UUID so retries are idempotent server-side.4.6 Back-office dashboardFR-4.6.1 Submission queue with filters: date range, zone, state, SMC, phase, engineer, survey type, review state, rejection type, flagged-only.4.6.2 Site Consolidated View (pre + post on one screen)The primary review surface. A post-survey approval marks the site Ready for IHS.FR-4.6.5.2 Back-office rejection — internal quality failure. Requires a reason code (Photos unusable / insufficient, Scope mismatch with pre-survey, Geolocation flagged, Incomplete form, Wrong site, Other) plus a mandatory free-text comment. Every revision is retained and viewable, so the reviewer can see what changed.FR-4.6.5.6 Rejection counts per site, per engineer, and per reason code are tracked and reportable — an IHS rejection rate is a delivery-quality KPI, and a back-office rejection rate is a training signal.FR-4.6.5.7 Marking a site Submitted to IHS (with date) is an explicit action, so the window between internal approval and client verdict is measurable.4.6.6 Review state machineStateMeaningSet byNext statesdraftOn the engineer's device, unsubmittedEngineersubmittedsubmittedReceived by server, awaiting internal reviewEngineer (sync)approved_internal, rejected_backofficerejected_backofficeFailed internal QA; rework requiredBack-officesubmitted (new revision)approved_internalPassed internal QA; ready to send to clientBack-officesubmitted_to_ihssubmitted_to_ihsPackage sent to IHS; awaiting client verdictBack-officeaccepted_ihs, rejected_ihsrejected_ihsClient rejected; rework requiredBack-office (recording client verdict)submitted (new revision)accepted_ihsClient accepted — terminal stateBack-office—FR-4.6.6.1 Transitions outside this table are rejected server-side, not merely hidden in the UI.FR-4.6.6.2 Every transition writes an audit record: from-state, to-state, actor, reason code, comment, timestamp.4.6.7 Dashboard overviewFR-4.6.7.1 KPI header: sites surveyed today, pre vs post split, closed vs WIP, awaiting internal review, awaiting IHS verdict, back-office rejections, IHS rejections, flagged submissions.FR-4.6.7.2 Per-engineer panel: sites assigned, pre/post completed, rejection rate, average days between pre and post.FR-4.6.7.3 Bulk selection for export and for bulk deck generation.FR-4.6.7.4 Site assignment screen: list all sites with current engineer, with single and bulk reassignment (§3.4).4.7 ExportsFR-4.7.1 — Daily Report XLSX. Architecture DecisionThis section answers the engineering question raised at kick-off: "Do I need an API, or should I connect the mobile directly to Cloudinary and MongoDB and use server actions to read the data for the back-office dashboard?"6.1 Option A — Direct Mongo + Cloudinary from Flutter (no backend)How it works: The Flutter app holds a MongoDB Atlas connection string (or Data API key) and a Cloudinary unsigned upload preset, and writes documents directly. The Next.js back-office reads MongoDB through server actions.ProsConsFastest possible prototypeCredentials ship inside the APK. A distributed Android binary is trivially decompiled; extracted keys grant write access to the entire database and image storeNo backend to deploy or maintainNo server-side validation — a modified client can write any document shape, corrupting the export pipelineOne less repositoryNo role enforcement; a field engineer's build can read and delete every other engineer's dataUnsigned Cloudinary presets allow anyone to upload arbitrary content and consume the quotaBusiness logic (pre↔post linking, geofence evaluation, status derivation) duplicated in the client and unenforceableKey rotation requires an app-store release for every deviceNo audit trail with a trustworthy actor identityVerdict: not viable. This is acceptable for a single-user internal prototype, never for a distributed field workforce whose submissions are commercial evidence of work performed.6.2 Option B — Next.js server actions + route handlers onlyHow it works: One Next.js application serves the back-office UI and exposes route handlers (/api/...) that the Flutter app calls. Secrets stay server-side. Server actions serve the dashboard's own data needs.ProsConsSingle deployable, single repositoryServer actions are a React/RSC transport — they are not a mobile-callable API. A Flutter client still needs route handlers, i.e. you build an API anyway, just less deliberatelySecrets stay on the serverLong-running work (PPTX/XLSX generation, bulk ZIP) fits poorly in serverless request timeouts; needs a separate worker regardlessFast to ship; good DXBackground jobs, queues, and scheduled digests need extra infrastructureVercel deployment is trivialMixing web-session auth (cookies) and mobile auth (JWT) in one surface tends to get messyLarge multipart photo uploads through serverless functions hit body-size limitsVerdict: viable for a lean v1, provided the mobile-facing route handlers are treated as a real, versioned, documented API from day one — and photo bytes go direct to Cloudinary via server-issued signatures rather than through the function.6.3 Option C — Dedicated API (Node.js + Express) + separate back-office client — SELECTEDHow it works:Flutter (offline queue)      │  HTTPS / JWT      ▼Node.js + Express API ──────► MongoDB Atlas      │  ├── signs Cloudinary upload params (mobile uploads bytes direct to Cloudinary)      │  ├── BullMQ + Redis worker → XLSX / PPTX generation      │  └── FCM push      ▲      │  HTTPS / JWTBack-office web client (Next.js or Angular)ProsConsOne authoritative place for validation, RBAC, geofence evaluation and status derivationTwo deployables instead of oneMobile never holds a database or Cloudinary secret; it receives short-lived signed upload paramsSlightly more initial setupIdempotent, versioned endpoints — essential for an offline queue that retriesRequires a hosting target with persistent processes (Render/Railway/Fly/EC2)Long-running export jobs run in a worker, off the request pathAssignment scoping and the review state machine are enforced in one place, not duplicated per clientMatches the team's stack (Node/TypeScript)The same API serves a future IHS client portal without reworkPhoto bytes bypass the API entirely — direct-to-Cloudinary keeps the API cheap and fast6.4 DecisionOption C is selected, implemented with Node.js + Express. The decisive factors are that (1) an offline-first mobile client requires idempotent, versioned, server-validated endpoints — retry semantics cannot live in the client alone, (2) survey submissions are commercial evidence, so server-side authorship, assignment scoping and audit are non-negotiable, (3) the two-tier review state machine must be enforced in exactly one place, and (4) document generation is long-running work that belongs in a worker.Option A is excluded on security grounds. Option B remains a viable interim only if the mobile-facing routes are designed as a proper API contract from day one.6.4.1 Express vs NestJS — note on the framework choiceExpress is the chosen framework. It is unopinionated and fast to move in, which suits a small team and a well-understood domain. The trade-off is that the structure NestJS provides out of the box (dependency injection, module boundaries, declarative validation pipes, guards, generated OpenAPI) must be established by convention instead. The mitigations adopted here:NestJS gives youExpress equivalent adopted in this projectDTO validation pipesZod schemas per route, applied by a shared validate(schema) middleware — no handler parses req.body directlyGuards + decorators for RBACrequireAuth, requireRole(...), and requireSiteAssignment middleware, applied at the router level so a route cannot be added unprotected by omissionModule boundariesFeature-folder layout (src/modules/<feature>/{routes,controller,service,repository,schema}.ts); controllers hold no business logic, services hold no Express typesGenerated Swaggerzod-to-openapi generating the spec from the same Zod schemas used for validation, so docs cannot drift from behaviourBuilt-in exception filterCentral error-handling middleware returning a consistent error envelope; typed AppError classesTesting utilitiesJest + Supertest against the app instance; service-layer unit tests with an in-memory MongoDBTypeScript is used throughout (not plain JavaScript) — the survey document is deeply nested and the review state machine benefits materially from compile-time checking.Upload pattern (applies to B and C)Mobile requests POST /uploads/signature with { surveyUuid, category, count }.Server returns a short-lived Cloudinary signature scoped to a folder (site-surveys/<siteId>/<surveyUuid>/before) with upload constraints (max bytes, allowed formats, max count).Mobile uploads bytes directly to Cloudinary — the API never proxies image data.Mobile posts the returned public_ids back to the API, which verifies each asset exists via the Cloudinary Admin API before attaching it to the survey.7. Open QuestionsResolved in v1.1: sites are pre-assigned to a named engineer via spreadsheet import (§4.1.1); the same engineer performs pre and post (§3.2); rejections are two-tier, both raised by the back-office user (§4.6.5); engineers see only their assigned sites, with reassignment supported (§3.4); the API is Node.js + Express (§6.4.1).Still open:Rejection rework scope — does a back-office rejection always require a physical re-visit, or can some cases (e.g. a missing comment, a mis-tagged photo) be corrected from the office by the supervisor? An office-correctable path would need a supervisor-edit capability distinct from engineer rework.IHS rejection granularity — is a client rejection always against the whole site, or can IHS reject specific work items? Item-level rejection would change the rework flow to a partial re-survey.Sites per engineer — can a site ever need two engineers (e.g. a large site split across a day)? The model currently assumes exactly one assignee per site.Assignment source of truth — once imported, does the spreadsheet remain authoritative (periodic re-import overwrites in-app reassignments), or does the platform become the master after first import? This determines whether re-import should be blocked from reverting a manual reassignment.Existing history — is there historical Excel data and are there past decks to migrate, and how far back?Deck fidelity — must the generated PPTX match the legacy deck's exact layout and branding, or is the improved labelled version (§4.7.2) acceptable to IHS?IHS submission channel — how is the package actually delivered to IHS today (email, portal, shared drive)? If it is a portal, Phase 4 integration may be worth pulling forward.Device ownership — company-issued devices (allows MDM and stricter policy) or BYOD?Photo adjustment limits — should brightness/contrast adjustment be capped or disabled entirely for evidence integrity, given the client relies on these photos as proof of work?12.
